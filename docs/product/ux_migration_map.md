# Карта UX-миграции: FamilyAI в ADR-next (UX Migration Map)

> [!IMPORTANT]
> Данный документ фиксирует требования к сохранению и эволюции пользовательского опыта (UX) при переносе функциональных сценариев из приватного продукта `family-ai` в публично-безопасный слой `agentic-domain-runtime` (ADR-next). Он служит приемочным контекстом для последующих этапов реализации runtime-платформы.

---

## 1. Инварианты миграции ADR-next (ADR-next Migration Invariants)

При переносе функционала в публично-безопасную среду ADR-next должны строго соблюдаться следующие технологические и продуктовые инварианты:

1. **Telegram как основной интерфейс**: Telegram остается основным интерфейсом взаимодействия для персональных/приватных инсталляций продукта.
2. **Свободный ввод как первый класс (Free-form first)**: Ввод на естественном языке остается основным способом взаимодействия. Не допускается регрессия к command-first UX (интерфейсу, требующему обязательного ввода слэш-команд для выполнения стандартных действий), кроме случаев, когда это явно согласовано.
3. **Модель общих семейных данных по умолчанию (Shared Family Data)**: Продукт ориентирован на одну семью с единым пространством данных. Не допускается преждевременное усложнение архитектуры в сторону публичного SaaS или многопользовательской изоляции (multi-tenancy) на уровне ядра.
4. **Обязательный этап подтверждения (Preview & Confirmation)**: Интерактивный предпросмотр (preview) и явное подтверждение (confirmation) перед сохранением данных в БД обязательны везде, где это реализовано в текущем UX, либо где этого требует безопасность данных (исключение случайных перезаписей/мусора).
5. **Стабильные технические ID агентов**: Внутренние промпты, лог-сообщения и системные вызовы оперируют только стабильными нейтральными идентификаторами агентов (`agent_id`). Пользовательские отображаемые имена (`display_name`) являются настраиваемыми.
6. **Доступность оффлайн-режима (Offline/Fake LLM)**: Система должна быть работоспособна в полностью оффлайновом/фейковом режиме (эмуляция ответов LLM из фикстур) без указания реальных API-ключей, что критично для тестирования и независимого ревью. Реальный режим работы с LLM подключается опционально через ключи.
7. **Явность изменений UX**: Любые изменения в поведении интерфейса для пользователя должны проектироваться и внедряться осознанно, а не возникать как случайные побочные эффекты технического рефакторинга.

## 2. Карта пользовательских сценариев (User Stories Map)

### Story 1: Telegram free-form input to Butler/domain routing
* **User story**:
  Как член семьи, я хочу писать сообщения в свободной форме боту, чтобы он автоматически распознавал тему запроса (кухня, книги, показатели здоровья, общие поручения) и перенаправлял мой запрос нужному специализированному агенту без необходимости вводить специальные команды.
* **Current family-ai UX**:
  Пользователь отправляет текстовое сообщение (например, *"запиши давление 120 на 80"* или *"хочу приготовить пасту"*). Бот вызывает Core Butler, который классифицирует запрос и автоматически активирует соответствующий FSM-сценарий нужного домена. Пользователю не требуется вводить слэш-команды.
* **ADR-next target UX**:
  Сохраняется аналогичное поведение. Свободный текст отправляется на вход Core Butler. В случае успешной классификации управление передается доменному обработчику. При неуверенной классификации пользователю предлагается интерактивное уточнение.
* **Preserve**:
  - Отсутствие требования вводить команды для начала диалога.
  - Фоновая классификация на стороне LLM.
* **Improve / change intentionally**:
  При неуверенной классификации вместо сухого системного сообщения *"Не удалось определить категорию"* выводить инлайн-кнопки с предложением выбрать домен вручную (например: `[Кухня]`, `[Книги]`, `[Здоровье]`, `[Другое]`).
* **Do not lose**:
  Поддержку сложных фраз и корректное перенаправление контекста сообщения в активируемый доменный сценарий.
* **User-level acceptance**:
  1. Пользователь вводит: *"добавь книгу Пикник на обочине автор Стругацкие"*.
  2. Бот перенаправляет запрос в домен книг и возвращает карточку-превью книги с кнопкой подтверждения.

### Story 2: Kitchen recipe capture: text/photo/voice batching, clarification, draft, preview, save/cancel, save-as-is
* **User story**:
  Как повар, я хочу отправлять текст рецепта, фотографии готового блюда или голосовые сообщения (в том числе пакетом/батчем), обсуждать детали с ассистентом, видеть интерактивное превью структурированного рецепта и сохранять его, отменять сохранение или записывать "как есть".
* **Current family-ai UX**:
  Пользователь может отправить одно или несколько фото с описанием или наговорить рецепт голосом. Бот группирует медиафайлы (сборка альбома), транскрибирует голос. Ассистент кухни разбирает состав и шаги, формируя черновик (draft) рецепта. Пользователь может в свободной форме дописать изменения (*"замени сахар на мед"*). После этого формируется финальный предпросмотр (preview). Пользователь нажимает инлайн-кнопку *"Сохранить"*, *"Отмена"* или *"Сохранить как есть"* (текст + фото без разбора LLM).
* **ADR-next target UX**:
  Опыт полностью переносится. Бэкенд накапливает поступающие в течение короткого окна (батчинг-интервал) сообщения (текст, фото, голос). LLM-агент формирует структурированный JSON рецепта. Пользователь видит красивое превью в чате Telegram с кнопками финализации.
* **Preserve**:
  - Батчинг медиа-групп (альбомов) и текста.
  - Транскрипция голосовых заметок.
  - Возможность корректировать черновик свободным текстом перед сохранением.
  - Кнопка сохранения исходного текста и фото "как есть" (без LLM-структурирования) при ошибках разбора.
* **Improve / change intentionally**:
  - Улучшить визуальное представление превью рецепта в чате, используя более структурированную разметку Markdown (выделение ингредиентов жирным шрифтом, нумерованный список шагов).
  - Сделать механизм сборки батчей независимым от конкретной библиотеки доставки сообщений (выделить в чистый core-сервис).
* **Do not lose**:
  Временное хранение медиа-файлов и текста черновика в FSM-контексте до момента явного подтверждения сохранения в постоянную БД.
* **User-level acceptance**:
  1. Пользователь отправляет 2 фото пирога и пишет: *"Яблочный пирог, выпекать 40 минут при 180 градусах"*.
  2. Бот присылает сообщение: *"Разбираю рецепт... [Превью]: Название: Яблочный пирог. Время: 40 мин. Шаги: 1. Выпекать..."* и кнопки `[Сохранить]`, `[Изменить]`, `[Как есть]`, `[Отмена]`.

### Story 3: Kitchen WebApp menu: cards, detail view, cook/edit/delete flow
* **User story**:
  Как пользователь, я хочу открывать визуальное меню (WebApp), просматривать карточки сохраненных рецептов, открывать детальную информацию, отмечать факт приготовления, редактировать ингредиенты и шаги или удалять рецепты.
* **Current family-ai UX**:
  В чате доступна кнопка, открывающая Telegram WebApp (React). В WebApp отображается сетка карточек рецептов с возможностью текстового поиска. Клик по карточке открывает полноэкранный просмотр рецепта с ингредиентами, фото и шагами. При нажатии на кнопку *"Приготовить"* счетчик приготовлений увеличивается. Кнопка *"Удалить"* запрашивает подтверждение. Кнопка *"Редактировать"* открывает форму изменения полей рецепта.
* **ADR-next target UX**:
  В чате отображается аналогичная кнопка WebApp. На бэкенде бьется защищенный эндпоинт, который валидирует подпись данных инициализации Telegram (Init Data). WebApp отображает список рецептов из публично-безопасного Supabase-инстанса. Действия "Cook", "Edit", "Delete" выполняются через API-запросы к ADR-next бэкенду.
* **Preserve**:
  - Валидацию сессии на основе Telegram WebApp Init Data.
  - Логику инкремента счетчика приготовлений.
  - Удаление только после подтверждения.
* **Improve / change intentionally**:
  - Использовать современный и чистый Vanilla CSS UI с адаптивной сеткой и плавными анимациями перехода.
  - Устранить жесткие стилистические зависимости от сторонних фреймворков, сделав дизайн более кастомизируемым.
* **Do not lose**:
  Безопасность выполнения мутаций: операции изменения и удаления должны быть доступны только пользователям с подтвержденными правами (принадлежность к семейной группе).
* **User-level acceptance**:
  1. Пользователь нажимает кнопку *"Меню"* в боте, открывается WebApp со списком блюд.
  2. Пользователь нажимает на рецепт *"Паста Карбонара"*, видит детали, нажимает *"Приготовили"* — счетчик увеличивается на 1, отображается анимация успеха.

### Story 4: Books capture / library progress на текущем уровне зрелости продукта
* **User story**:
  Как читатель, я хочу быстро сохранять книги в свою семейную библиотеку, а также обновлять статус чтения и текущий прогресс (на какой я странице).
* **Current family-ai UX**:
  Пользователь может ввести команду `/book` или написать в свободной форме название книги. Система предлагает два пути: автоматический разбор через LLM-агента или пошаговый ручной ввод (Название -> Автор -> Описание). После сохранения пользователь может обновлять прогресс (например, *"прочитал 45 страниц книги ИмяКниги"* или через интерактивное меню).
* **ADR-next target UX**:
  Сохраняются обе ветки сбора информации о книге (LLM-ассистент и пошаговый FSM-опросник). Обновление прогресса чтения происходит через текстовый ввод или инлайн-меню книги в чате.
* **Preserve**:
  - Ручной пошаговый FSM-сценарий сбора как обязательный fallback при выключенном LLM-провайдере.
  - Хранение связей авторов и книг.
* **Improve / change intentionally**:
  Сделать интерактивное отображение прогресса чтения книги в чате с использованием текстового прогресс-бара (например, `||||||||░░ 80%`).
* **Do not lose**:
  Нормализацию имен авторов во избежание дублирования записей (например, "А. Стругацкий" и "Аркадий Стругацкий" должны сопоставляться корректно).
* **User-level acceptance**:
  1. Пользователь пишет: *"/book"* -> выбирает *"Ввести вручную"*.
  2. Бот последовательно запрашивает: Название, затем Автора, затем Описание, после чего выводит превью книги и кнопку `[Сохранить в библиотеку]`.

### Story 5: Medical/health capture как event logging, not clinical advice
* **User story**:
  Как пользователь, я хочу быстро фиксировать показатели здоровья (давление, пульс, уровень сахара) и симптомы для личного дневника, будучи уверенным, что система не пытается ставить диагнозы и не заменяет консультацию врача.
* **Current family-ai UX**:
  Пользователь пишет: *"давление 120/80"* или *"сахар 5.2"*. Бот распознает метрику, извлекает числовые значения, определяет время измерения (по умолчанию текущее) и спрашивает, для кого записать показатель (выбор члена семьи). После подтверждения данные сохраняются в БД. Сообщения бота не содержат медицинских рекомендаций, диагнозов или выводов.
* **ADR-next target UX**:
  UX сбора полностью сохраняется. На этапе вывода превью перед сохранением явно отображается неклинический дисклеймер (event logging). Все параметры валидируются на разумные диапазоны (например, пульс в пределах 30-250 уд/мин).
* **Preserve**:
  - Четкое разделение сбора по типам метрик (давление, глюкоза, общая заметка).
  - Выбор/подтверждение субъекта (члена семьи), для которого вносится запись.
  - Отсутствие каких-либо клинических советов или интерпретаций результатов в ответах бота.
* **Improve / change intentionally**:
  Явно выводить краткий дисклеймер-предупреждение в футере сообщения с превью показателей: *"Данные сохранены в журнал. Программа не является медицинским средством"*.
* **Do not lose**:
  Строгую валидацию вводимых вручную значений на бэкенде для исключения опечаток (например, случайного ввода давления 1200 вместо 120).
* **User-level acceptance**:
  1. Пользователь пишет: *"сахар 5.8 перед обедом"*.
  2. Бот присылает превью: *"Тип: Глюкоза. Значение: 5.8 ммоль/л. Контекст: Перед едой. Субъект: Алексей. Записать? [Да] [Отмена]"*.

### Story 6: Shared family data model
* **User story**:
  Как член семьи, я хочу, чтобы все добавленные рецепты, книги и показатели здоровья были автоматически доступны всей моей семье, чтобы нам не нужно было настраивать права доступа или делиться ссылками.
* **Current family-ai UX**:
  Все авторизованные пользователи бота работают с единой базой данных. Рецепты, книги и показатели здоровья видны всем членам семьи. Данные о здоровье разделяются по именам членов семьи, но хранятся в единой таблице и доступны для просмотра всей семье.
* **ADR-next target UX**:
  Модель совместного семейного доступа остается основной. Система разворачивается в рамках одного семейного инстанса. База данных содержит общие таблицы без изоляции пользователей друг от друга внутри инстанса.
* **Preserve**:
  - Модель данных "один инстанс — одна семья" (single-tenant shared family model).
  - Защиту доступа к API бэкенда и БД на уровне идентификаторов разрешенных пользователей Telegram.
* **Improve / change intentionally**:
  Обеспечить чистую структуру схемы базы данных в публичном ADR-next с использованием публично-безопасных пространств имен (namespaces) без жестко зашитых приватных идентификаторов.
* **Do not lose**:
  Политики Row-Level Security (RLS) в Supabase, которые должны проверять принадлежность пользователя к разрешенному списку участников семейного чата/инстанса.
* **User-level acceptance**:
  1. Член семьи 1 добавляет рецепт через бот.
  2. Член семьи 2 открывает WebApp и сразу видит этот рецепт в списке.

### Story 7: User-provided LLM key flow
* **User story**:
  Как администратор личного инстанса, я хочу предоставить собственный API-ключ Gemini/Google для работы интеллектуальных функций бота, либо иметь возможность запустить систему в безопасном оффлайн-режиме без ключей для ознакомления и тестирования.
* **Current family-ai UX**:
  Ключ жестко прописан в файле `.env` на сервере. При его отсутствии бот падает с ошибкой инициализации клиента Google GenAI при попытке обратиться к LLM.
* **ADR-next target UX**:
  Пользователь настраивает ключи через переменные окружения или вводит их интерактивно при установке. Если ключи не предоставлены, система автоматически активирует безопасный оффлайн-режим (`offline/fake mode`), где вызовы LLM перенаправляются на детерминированные моки, возвращающие синтетические ответы из тестовых фикстур. Это позволяет запустить и проверить систему без реальных API-запросов.
* **Preserve**:
  Использование переменных окружения как основного источника конфигурации в проде.
* **Improve / change intentionally**:
  - Автоматическое переключение в `fake` режим при отсутствии переменных ключей с логированием информационного предупреждения вместо падения приложения.
  - Интерактивный CLI-запрос ключа при локальном развертывании (bootstrap) с маскированием ввода (скрытие символов при вводе).
* **Do not lose**:
  Маскирование ключей в логах и файлах конфигурации. API-ключи никогда не должны записываться в логи приложения или сохраняться в незашифрованном виде в файлах состояния установки (таких как `.adr_bootstrap_state.json`).
* **User-level acceptance**:
  1. Администратор запускает установку `doctor` CLI без установленного ключа.
  2. CLI сообщает: *"Gemini API Key: [MISSING] - Switching to OFFLINE/FAKE mode. Real LLM extraction will be emulated"*. Система успешно запускается.

### Story 8: User-configurable agent display names
* **User story**:
  Как владелец инстанса, я хочу иметь возможность переименовать виртуальных ассистентов (например, назвать Дворецкого "Помощником", а Ассистента кухни "Шефом"), чтобы общение с ними выглядело более естественно и персонализированно для моей семьи, при этом технический код не должен ломаться от изменения имен.
* **Current family-ai UX**:
  Имена ассистентов жестко зашиты в системные промпты и логику формирования ответов бота (например, бот всегда представляется конкретными персональными именами).
* **ADR-next target UX**:
  В публичном коде и внутренних логах используются исключительно стабильные нейтральные идентификаторы агентов (например, `core.butler`, `kitchen.recorder`). Отображаемые имена агентов (`display_name`) вынесены в конфигурационные файлы (YAML) или в БД. Ответы бота формируются с динамической подстановкой настроенного `display_name`.
* **Preserve**:
  Использование стабильных `agent_id` в промптах и логах для поддержания качества классификации LLM.
* **Improve / change intentionally**:
  - Полное отделение личных/семейных имен агентов от исходного кода ядра.
  - Настройка имен через централизованный конфигурационный файл инстанса.
* **Do not lose**:
  Консистентность промптов: LLM-модели должны получать стабильные инструкции относительно своей роли, а подстановка кастомного имени должна происходить на этапе формирования сообщения пользователю, чтобы не ломать системные инструкции агента.
* **User-level acceptance**:
  1. Администратор устанавливает `kitchen.recorder.display_name = "Шеф-Повар"` в `config.yaml`.
  2. При разборе рецепта бот отвечает: *"**[Шеф-Повар]**: Я подготовил черновик рецепта..."*.

## 3. Контракт конфигурации и использования LLM-ключей (LLM Key UX/Config Contract)

Для обеспечения безопасности и гибкости при работе с ключами LLM в ADR-next утверждается следующий контракт:

1. **Разрешенные источники (Accepted Sources)**:
   - Переменные окружения: `GEMINI_API_KEY` и/или `GOOGLE_API_KEY`.
   - Маскированный интерактивный ввод через CLI при выполнении процедур установки/настройки (`bootstrap`).
2. **Приоритет и Предупреждения (Precedence & Warnings)**:
   - **Канонический источник (Canonical Source)**: В качестве канонического целевого ключа (Canonical Target Key) в ADR-next принимается `GEMINI_API_KEY` (как product-facing имя, соответствующее семейству моделей Gemini). Переменная `GOOGLE_API_KEY` поддерживается в качестве обратимо-совместимого псевдонима (backwards-compatible alias).
   - **Явный выбор и предупреждение**: При одновременном наличии обеих переменных окружения (`GEMINI_API_KEY` и `GOOGLE_API_KEY`) в конфигурации приложения:
     - Приложение обязано вывести контролируемое предупреждение (`Warning`) в логи: `"Both GEMINI_API_KEY and GOOGLE_API_KEY are set. Explicitly using GEMINI_API_KEY as the canonical key and bypassing SDK auto-detection."`.
     - Приоритетным источником признается `GEMINI_API_KEY`.
   - **Требование к реализации (Target Implementation)**: Целевая реализация должна явно передавать выбранный на уровне конфигурации приложения ключ в конструктор SDK-клиента (например, через явный параметр `api_key`), полностью исключая и переопределяя встроенные в SDK механизмы неявного автоопределения ключей. Недопустимо полагаться на внутренний precedence SDK или операционной системы.
   - **Текущее поведение и легаси-ограничение (Current-State Caveat)**:
     - В текущей реализации `family-ai` конфигурация `src/bot/config.py` использует Pydantic-настройку `AliasChoices("GEMINI_API_KEY", "GOOGLE_API_KEY")`.
     - При одновременном наличии обеих переменных в окружении Google GenAI SDK по умолчанию отдает приоритет `GOOGLE_API_KEY` и выводит в stderr предупреждение: `"Both GOOGLE_API_KEY and GEMINI_API_KEY are set. Using GOOGLE_API_KEY."`, в то время как `src/bot/integrations/llm_client.py` явно передает `api_key=self.config.gemini_api_key`. Это создает конфликт поведения и неявную зависимость от внутренней логики библиотеки. Данное поведение является легаси-артефактом и в ADR-next заменяется на явное управление приоритетом на стороне приложения.
3. **Безопасность хранения и вывода (Never Leak Secrets)**:
   - Запрещено выводить значения ключей в консоль, логи или записывать в коммиты.
   - Файл состояния инициализации `.adr_bootstrap_state.json` должен хранить только метаданные о факте предоставления ключа и его источнике, но **никогда сам ключ**:
     ```json
     {
       "gemini_key_provided": true,
       "gemini_key_source": "env.GEMINI_API_KEY",
       "configured_at": "2026-06-04T11:52:31Z"
     }
     ```
   - Переменные облачного окружения (например, Render env vars) получают значения секретов исключительно во время выполнения явной команды применения (`apply`).
4. **Поведение по умолчанию**:
   - По умолчанию для прохождения ревью и тестов используется `offline/fake` режим, не требующий внешних сетевых запросов.

## 4. Контракт реестра агентов и отображаемых имен (Agent Registry Contract)

Для гибкой настройки персонализации без изменения кода ядра утверждается следующий контракт реестра агентов:

1. **Реестр стабильных ID**:
   Все агенты в системе регистрируются под уникальными стабильными идентификаторами:
   - `core.butler` — классификация и маршрутизация входящих сообщений.
   - `kitchen.recorder` — разбор, уточнение и сохранение рецептов.
   - `books.librarian` — каталогизация книг и ведение прогресса чтения.
   - `health.recorder` — ведение журнала показателей здоровья и симптомов.
2. **Конфигурация отображаемых имен (Configurable display_name)**:
   - Каждому `agent_id` соответствует настраиваемое свойство `display_name`.
   - Публичные значения по умолчанию являются нейтральными (например, *"Ассистент кухни"*, *"Библиотекарь"*).
   - В приватной инсталляции кастомные имена переопределяются через локальный файл конфигурации `config.yaml` или системную таблицу БД.
3. **Внутреннее использование**:
   - Во внутренних логах разработки, промптах для LLM и метаданных сессий всегда используются только стабильные `agent_id`.
   - Подстановка `display_name` осуществляется исключительно в шаблонах сообщений, отправляемых конечному пользователю в Telegram.
