# Runbook: Local Supabase Design & Verification Path

This document outlines the optional local Supabase verification path for reviewers who wish to evaluate the persistence layer and security policies in a live database runtime rather than relying solely on the default offline sandbox.

> [!IMPORTANT]
> The **offline sandbox remains the default and recommended reviewer path**. It runs in-memory and does not require Docker, Supabase, or any external infrastructure. The local Supabase path is completely optional and intended for deeper security and architectural validation.

---

## 1. Architectural Decision: Supabase Local-First

We have chosen a **Supabase local-first** approach over a plain PostgreSQL-only setup. While plain PostgreSQL would allow simple schema evaluation, it lacks the context of the Supabase lineage:
* **RLS & Auth integration**: Supabase natively integrates PostgreSQL Row Level Security (RLS) with its identity service (`auth.users`), which is critical for verifying our multi-tenant and multi-user security boundaries.
* **API Parity**: Exposing schemas via PostgREST (auto-generated REST API) is a key architectural feature of the production stack.
* **No Cloud Dependency**: The local Supabase path runs entirely on your local machine and does **not** require a Supabase cloud account or internet access after the initial CLI setup.

---

## 2. Target Directory Structure

For future runnable integration, the database assets will be organized as follows:

```text
supabase/
  config.toml        # Local Supabase service configurations and API schema exposures
  migrations/
    0001_schema.sql  # Database schema definitions and DDL scripts
  seed.sql           # Synthetic seed data for testing
```

> [!NOTE]
> Currently, the conceptual schema definitions and synthetic seeds are located in [schema_sketches.sql](schema/schema_sketches.sql) and [synthetic_seeds.sql](schema/synthetic_seeds.sql).

---

## 3. Conceptual Commands for Local Verification

To run and verify the schema locally, a reviewer would execute the following standard CLI commands:

```bash
# Initialize the Supabase project configuration
supabase init

# Start the local Docker-based Supabase stack (creates PostgreSQL, Auth, REST API, etc.)
supabase start

# Apply database migrations and seeds to reset the local database state
supabase db reset

# Perform quick smoke checks on the auto-generated REST endpoint
curl -X GET "http://localhost:54321/rest/v1/dishes" \
  -H "apikey: <anon_key>" \
  -H "Authorization: Bearer <anon_key>"
```

## 4. Compatibility Gaps & Decision Table

To transition the existing conceptual schemas in [schema_sketches.sql](schema/schema_sketches.sql) to a fully executable local Supabase state, the following design decisions are established:

| Component | Current Sketch Status | Local Supabase Mapping | Decision / Action |
| :--- | :--- | :--- | :--- |
| **Schema Qualification** | Uses logical namespaces (`core`, `kitchen`, `books`, `med`, `api`). | Supabase exposes the `public` schema via API by default. | **Adapt**: Add custom schemas (`core`, `kitchen`, etc.) to the `api.schemas` list in `config.toml` to expose them securely. |
| **RLS Policies** | Conceptual policies verify request variables. | Requires real PostgreSQL policies using `auth.uid()` or JWT claims. | **Adapt**: Update RLS policies to check the requesting user's `auth.uid()` against profile mapping tables. |
| **`auth.uid()` Assumptions** | Omitted; tables use sequential integer IDs for keys. | Users are identified by UUID keys generated by `auth.users`. | **Adapt**: Introduce a UUID reference field in `core.app_users` mapping to the Supabase `auth.users.id`. |
| **Telegram IDs vs. Auth Users** | Primary user tracking relies on `telegram_user_id` (bigint). | API calls are authenticated via Supabase JWT corresponding to an auth user. | **Keep & Adapt**: Maintain `telegram_user_id` for state tracking, but associate it with the `auth.users` UUID for API boundary authorization. |
| **Storage Placeholders** | Paths refer to local strings (e.g., `attachments/kitchen/onion_soup_main.webp`). | Objects must be served from Supabase Storage buckets. | **Postpone**: Maintain text placeholders in seeds; transition to Storage object reference URLs during runtime client integration. |
| **`api` Schema Tables** | Contains conceptual `token_scopes` and `request_logs` tables. | API authentication and rate-limiting are handled by Kong. | **Postpone**: Treat as regular tables for telemetry validation; do not hook into Supabase API Gateway configuration for initial steps. |

## 5. Reviewer Value Statement

Running a local Supabase instance provides several advantages over the offline sandbox:
1. **DDL and Syntax Validation**: Guarantees that all tables, constraints, foreign keys, and indexes compile perfectly on a standard PostgreSQL engine without mocking.
2. **RLS Verification**: Allows active testing of policy boundaries by simulating requests with different mock JWT tokens to ensure data separation.
3. **API Integrity**: Demonstrates the direct mapping of the database structure to the auto-generated PostgREST endpoints, verifying client-to-database communication interfaces.
